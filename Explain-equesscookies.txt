The browser's call for the relative URL /api/auth/status/ goes out to the server on http://127.0.0.1:3000. That call is handled by the Next.js server (still at http://127.0.0.1:3000). Because the URL starts with /api/, the middleware does not add a locale substring, and the rewrite configuration proxies the request to the backend, creating a corresponding request to http://127.0.0.1:8000/api/auth/status/. This proxying is possible because it happens server-side inside Node, not inside the browser, and therefore it is not subject to the browser’s same-origin restrictions. Those restrictions are enforced by the browser itself. 

Node.js, by the way, (usually just called “Node”) is a JavaScript runtime that runs outside the browse. Normally, JavaScript runs in a browser. Node lets you run JavaScript on a server or your local machine.

It’s built on Google’s V8 engine (the same engine Chrome uses), but it gives you access to filesystem, network, and OS-level features that browsers don’t allow. Node runs on the server side inside Next.js.

In theory, it would be possible for someone to write a browser that ignores the cross-origin-request restrictions, but the purpose that browsers have to enforce them is to protect their users from malicious websites, not, say, to prevent hackers from making cross-origin-requests.  In fact, tools such as curl and similar allow their users to do precisely that.

A cookie is a record stored by the browser and associated with a particular hostname (domain), not with a physical or conceptual machine, or with a port number. It typically contains a key-value pair (in the case of the session cookies we're discussing it is sessionid=alphanumericcode). It will also have a variety of metadata, including path and security flags. Importantly, cookies are tied to the literal hostname string. This means that a cookie associated with 127.0.0.1 will not be sent when visiting localhost, even though both refer to the same machine. From the browser’s perspective, the two addresses are different domains. As we say, though, Cookies are not associated with a port on the same machine (physical or conceptual); a cookie for http://127.0.0.1 will apply to both http://127.0.0.1:3000 and http://127.0.0.1:8000 (and indeed to any other port on the same address string). When a cookie's data is sent to Django, Django uses the key-value pair to look up what it is the cookie is referring to. In our case, the relevant information is the username for the session, whether or not they're a superuser and whether they're authenticated.

When Django creates a session cookie, it first generates a unique session key and stores all the relevant session data (username, authentication status, superuser flag, etc.) in its session store on the server, usually a database table. It then sends the session key to the browser in a Set-Cookie header. The browser receives this header and stores the cookie locally, associating it with the exact hostname and path specified by Django. From that point on, the browser automatically includes the session cookie in the Cookie header of every request to matching URLs, allowing Django to look up the session key and reconstruct the user’s session. The cookie itself contains only the key-value pair; all the metadata, such as HttpOnly, Secure, SameSite, and expiration, stays in the browser and governs when and how the browser sends the cookie. In essence, the browser “owns” the cookie, carrying it silently with requests, while the server retains the authoritative session data linked to that key.

When the browser makes a GET request to /api/auth/status/, it automatically includes the session cookie in the request headers. In development, that request first goes to the Next.js server running on 127.0.0.1:3000. Because the URL starts with /api/, the server’s middleware recognizes it as an API call and proxies it to the backend at 127.0.0.1:8000, including the same headers, and therefore the same session cookie. Django receives the request with the cookie, reads the session key, and looks up the corresponding session data in its store. It then constructs a JSON response containing the user’s information—username, authentication status, and superuser flag—and sends it back to the Next.js server. The middleware forwards this response unchanged to the browser, which uses it to update the UI, showing login or logout buttons appropriately. At no point does the cookie leave the browser except as part of the request headers, and at no point does the server need to create a new cookie just to read session data.
